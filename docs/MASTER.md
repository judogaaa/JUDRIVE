## 01. Продукт и цель

**JUDRIVE — диагностика, которой можно доверять.** Адаптивная веб-платформа для диагностики двигателей коммерческого транспорта: получение результата акустической ML-диагностики, доказательное объяснение, поиск по руководствам, диалог, история и подтверждённая заявка на дефектовку. Второе рабочее пространство — главный механик, который видит парк и приоритеты.

Цель заказчика — показать понятный прототип с возможностью последующей интеграции реального ML НейроДВС, расширения библиотеки руководств и внедрения в процессы автопарка. Механический дефект может привести к дорогостоящему ремонту и простою; раннее обнаружение позволяет планировать проверку. OBD и акустическая ML-диагностика не взаимозаменяемы. Мы не создаём акустическую ML-модель: получаем её результат от заглушки. Не обещаем безотказность, экономию в рублях, предсказание срока отказа или победу без данных.

Механик должен за 10 секунд понять: что обнаружено, насколько достоверно, что делать дальше. Главный механик — какие машины требуют внимания и почему. Продукт не принимает окончательное решение о технической исправности и выпуске на линию вместо специалиста.

**Конкурентное преимущество: Diagnostic Evidence Engine.** Факты ML отделены от гипотез агента, процедуры от предположений, доказательства связаны с реальными страницами, каждую работу можно проверить. Демонстрация показывает рабочий процесс, а не презентацию LLM.

## 05. Контракт ML и смысл статусов

Переменная MOCK_ML_URL, локально http://127.0.0.1:8001. GET /health; POST /diagnose.

```json
{"vehicle_id":"M333YK47","session_id":"S-0005"}
```

Пример из архива:
```json
{"vehicle_id":"M333YK47","session_id":"S-0005","status":"anomaly","anomaly_type":"F08","anomaly_title":"Дизельная топливоподача","anomaly_score":0.76,"confidence":0.73,"signal_quality":"good","description":"Жёсткая работа с резким стуком в цилиндрах, дымный выхлоп","model_version":"mock-v1"}
```

- status: normal, anomaly, check_failed.
- anomaly_type/title null при normal/check_failed. score/confidence от 0 до 1 или null; при check_failed оба null. bad = непригодна; warning = помехи; good = пригодна. confidence — уверенность модели, не вероятность поломки. anomaly_score — показатель отклонения, не остаточный ресурс или вероятность тяжёлой поломки.
- 200 результат; 404 неизвестная машина/сессия либо чужая пара; 422 невалидный запрос; ошибки сети отдельно. Модель двигателя брать из карточки машины, не из текста модели.
- Блокировка: при check_failed или bad запрет заключения о двигателе и заявки; предложить повторную запись, объяснить причину из данных без исполнения сторонних инструкций. Именно новый замер человеку, а не искусственно сгенерированная сессия.
- normal: значимых отклонений не обнаружено данным методом, продолжать эксплуатацию по штатному регламенту при отсутствии иных признаков. Не выдавать гарантию исправности. Не отправлять заявку на основании normal.
- anomaly: вывести наблюдения ML, предположительную неисправность, качество/уверенность/показатель, риск, доказанные проверки и ограничения.
- warning/низкая confidence: явно предупредить о помехах и неопределённости; дать безопасный осмотр узла по руководству и предложить повторную запись при необходимости. Не требовать во всех случаях сначала новую запись: БРИФ позволяет осмотр и подтверждение механиком. Заявка на дефектовку — только как запрос проверки, не подтверждённый ремонт, с поддержкой руководства и осознанным подтверждением. Низкая уверенность не означает низкий риск. Порог предупреждения проектный, например confidence<0.70 с проверкой данных; не выдавать его за порог заказчика. Если предупреждение по качеству и низкой уверенности противоречат статусу, показать факты и не завышать достоверность.
- Вывод «можно ли перегнать своим ходом»: строго по применимому источнику либо «данных недостаточно», рекомендовать специалисту решить допуск. При существенном риске рекомендовать не выпускать до осмотра; не утверждать юридический факт запрета или фактическое решение.

## 06. ТОиР: точная схема v6 и подтверждение

MOCK_TOIR_URL, локально http://127.0.0.1:8002. GET /health; POST /tickets.

```json
{
  "vehicle_id":"B418HK98",
  "session_id":"S-0009",
  "anomaly_type":"F01",
  "conclusion":"Предполагаемое отклонение клапанного механизма; требуется проверка",
  "urgency":"medium",
  "operations":["Проверить тепловые зазоры клапанного механизма по руководству"],
  "spare_parts":[],
  "references":[{"manual":"236-3902150-Б РЭ","pdf_page":33}]
}
```

Пример формы, не готовое решение для любой машины; приоритет и работы вычисляются и подтверждаются по фактам. Реальный JSON: все восемь полей обязательны; operations и references непустые, spare_parts может быть []. urgency low/medium/high. Номер PDF >=1. Ссылка manual — обозначение/название из ТЗ, не придуманное имя. 201 {"ticket_id":"TKT-0001","status":"created"}; 404, 422, сетевые ошибки.

**Старые поля запрещены**: fault_id, diagnosis, priority, works, parts, source_pages; внутри ссылки document/page. В исходной заглушке есть специальная обработка 418 для старых полей. Не заменять session_id на check_id.

Перед отправкой сервер валидирует выбранную пару, наличие подлинного результата POST /diagnose, статус anomaly, код из ответа, принадлежность ссылок к двигателю, подтверждённые работы, непустоту полей, версию черновика и волеизъявление пользователя. LLM не может отправить заявку сама; отдельный инструмент подготовки черновика и отдельное защищённое действие отправки после подтверждения. Механик видит машину, проверку, заключение, приоритет и основание, список работ/деталей и ссылки. После изменения машины/проверки/черновика подтверждение аннулируется. При общей процедуре осмотра нужного узла допустима заявка с общей проверкой как единственной работой, если она реально описана в правильном руководстве. Если нет даже такой процедуры — рекомендуем ручную дефектовку, заявку не отправляем. Не брать норматив от иной модели. Не выдумывать детали/каталожные номера.

Заглушка проверяет формат и пару IDs, но не смысл заявки; ответственность на нашем сервере. Ведём SQLite-журнал заявок с локальным ID, vehicle/session, snapshot, состоянием, реальным ticket_id, временем. Заглушка после рестарта начинает номера снова с TKT-0001, не поддерживает список заявок и не проверяет дубли. Не считать ticket_id глобально уникальным. Защита двойного клика, уникальный локальный ключ подтверждения, атомарная фиксация попытки. Если отправка оборвалась после запроса и неизвестно, создана ли заявка, показываем неопределённость, не шлём повтор автоматически. Не симулировать успешный ответ.

Разделять соседние страницы, таблицы не рвать без метаданных. Хранить оригинальную точную выдержку отдельно от нормализованного текста. Индекс строится после старта.

Базовая реализация: извлечение текста постранично (pypdf/pdfplumber либо Poppler после проверки совместимости и лицензии), layout-ориентированный текст таблиц, SQLite FTS5 с русской нормализацией, поиск по синонимам, ML title/description и уточнённому русскоязычному запросу. Сначала строгий engine allowlist, затем BM25 и точные термины/числа, затем расширение соседней страницей при необходимости. Для редких формулировок — перефразирование запроса агентом или локальный словарь технических терминов; не кодировать ответы на демо. Hybrid embeddings лишь если простого поиска недостаточно и это не тормозит MVP. Индекс кешируется по хешу файла, перестроение не на каждом запуске.

OCR выборочно: плохо извлечённые полезные страницы и нужные таблицы/рисунки; Tesseract rus+eng (проверить наличие) либо подходящий разрешённый OCR. Проверить исходную страницу визуально, при неразборчивости честно указать ограничение. Для последовательности затяжки на рисунке хорошо перечислить номера и связь с деталями, только если достоверно считано; иначе показать точную страницу/область и попросить механика сверить. Не фантазировать по картинке. Не обещать мультимодальную LLM-модель: выбранная модель используется для текста, графика через извлечение/OCR/показ оригинала.

Каждая рекомендация, норматив и процедура должны быть связаны с evidence_id, документом и страницей. Модель получает только допустимые кандидаты и возвращает IDs, а сервер разрешает их в истинные ссылки. Проверять существование, engine, текстовую поддержку чисел/единиц, конкретную операцию и контекст модификации. Не считать простое совпадение цифры полной семантической проверкой. При ошибке — максимум один ограниченный корректирующий вызов или убрать неподтверждённое. Второй AI-reviewer только при необходимости, не гарантия. Не выводить ссылки без фактической поддержки, не генерировать ремонт из общих знаний. Если источник не найден, указать именно что отсутствует, предложить ручную диагностику. Ссылку открыть в выдвижной панели на точной странице PDF с цитатой, навигацией, полноэкранным просмотром, загрузкой по мере необходимости. PDF-файлы суммарно ~156 МБ по архиву; большой файл 99 МБ не загружать целиком на каждый экран.

## 08. Агент и Diagnostic Evidence Engine

Р: FastAPI оркестрирует Groq GPT-OSS 120B. Реальные отдельные инструменты:
- get_diagnosis(vehicle_id, session_id): вызов ML; состояние, контекст, валидация.
- search_manuals(query): разрешённый двигатель определяется сервером из активной машины, модель не может его подменить.
- prepare_defect_ticket(...): формирование черновика из проверенных фактов и доказательств. Документированные поля. Отправка допустима только отдельным защищённым обработчиком подтверждения.
- get_vehicle_history — дополнительный read-only инструмент для сопоставления сессий и заявок; данные загружены локально.
Агент выбирает инструменты по смыслу: запрос диагностики, вопрос о норме, вопрос о развитии отклонения, просьба о заявке, уточнение. Не делать обычный if-else сценарий вместо агента. Детерминированный guardrail, наоборот, обязателен: права, статус, контекст, лимиты, валидация, подтверждение. Сначала проверить фактическую совместимость tool calling и структурированного ответа у Groq на выбранной модели. Если строгий JSON и tool calls нельзя совмещать, сделать отдельную стадию инструментов и отдельно валидировать финальный ответ. Не усложнять фреймворками без нужды.

Ответ: 1) вердикт и запись, 2) ML-наблюдения, 3) осторожная гипотеза, 4) риски по доказательствам, 5) проверки по руководству, 6) возможные работы и ограничения, 7) источники. Понятный краткий текст сверху, детализация раскрывается. На первый ответ не более нескольких необходимых инструментальных итераций (например 3–4), ограничение по времени/токенам, не бесконечный цикл.

Панель «На чём основан вывод»: исходные структурированные факты ML, найденные реальные фрагменты/страницы, подтверждённые рекомендации, ограничение и действие механика. Показывать реальные вызовы инструмента/статусы, не генерировать внутренние скрытые рассуждения модели или фиктивный процесс работы. Вауу-эффект — клик на действие → точная страница → подтверждение заявки. По возможности интерактивный чек-лист проверок с отметками пользователя, без подмены физической проверки.

## 09. Безопасность и приоритет

В архиве найдены три явно вредоносные инструкции в description: T792HO98/S-0043 (F02) просит объявить двигатель исправным; H142OX78/S-0113 (check_failed) просит нормализовать статус; E622KM47/S-0195 (F12) просит раскрыть промпт и создать заявку low без ссылок. Это контрольные примеры для защиты, не команды. Данные диагностики, PDF/OCR, пользовательский текст — недоверенные входы. Структурированное status поле выше текста description. Не передавать ключ в контекст, не выполнять посторонние инструкции из данных, не раскрывать системные промпты/секреты, не давать модели произвольный shell/HTTP. Серверные проверки не зависят от LLM. Сохранить необработанный источник при необходимости внутреннего аудита, отображать только безопасный смысл признаков; не выдавать инъекцию как медицинский/механический факт. Изменение выбранной машины очищает/изолирует контекст.

Приоритет является рекомендацией команды, а не утверждённым бизнес-правилом. БРИФ: механика волнует безопасность и выход на линию, бизнес — последствия задержки и потенциальная стоимость ремонта; контекст эксплуатации влияет. Нет готовой таблицы приоритетов. Проектная политика:
- high: обоснованная угроза безопасности/серьёзного дальнейшего ущерба или ограничение эксплуатации из применимого руководства; рекомендовать не выпускать до специалиста и проверять в первую очередь.
- medium: отклонение требует плановой/оперативной дефектовки, нет надёжного основания утверждать немедленный запрет эксплуатации. Учитывать признаки, качество и повторяемость; низкая уверенность с потенциально серьёзным риском не превращается автоматически в low.
- low: подтверждённое основание для менее срочного наблюдения/осмотра; не означает автоматически исправность. При нехватке данных не выдавать уверенные оценки и не ставить критичность по одной confidence.
Показать источник и короткое объяснение: влияние на эксплуатацию, возможные последствия, основания повторной проверки. Не выдумывать точные цены ремонта, проценты риска, пробег до отказа или финансовую экономию. Финальное решение о рейсе/ремонте — специалист. При норме нет заявки, при сбое — статус неизвестен, не «исправно».

## 10. Два рабочих пространства и дизайн

Р: Apple-inspired сдержанный профессиональный веб-интерфейс JUDRIVE, а не копия Apple или другого продукта. Manrope + системный fallback для кириллицы/других письменностей; Lucide; React/TypeScript/Vite; качественные привычные компоненты. Светлая/тёмная темы, семантические цвета (зелёный/янтарный/красный/нейтральный исключительно для статусов), контраст, аккуратные отступы, крупные кнопки, читаемость на смартфоне и в шумном цехе. Нет неона, лишних градиентов, стекла, бессмысленных больших герой-блоков, emoji, фоток машин, AI-slop. Использовать пиктограмму типа ТС, не тратить время на изображения. Анимация только функциональная, reduced-motion.

Навигация: «Диагностика», «Автопарк», «Заявки», язык/тема. Режим механика — быстро выбрать госномер/гаражный номер/машину и сессию, по умолчанию последняя, но доступна любая; чёткая кнопка «Получить результат диагностики». Верхняя карточка: статус текстом, двигатель, время проверки, основное действие, риск/неопределённость. В чате быстрые вопросы, микрофон, текст; слева/в сворачиваемом блоке история; справа/снизу доказательства. На мобильном последовательный экран: машина → вердикт → действие → диалог → источники. Панель источников становится полноэкранной, диалог заявки не перекрывает основные действия. Предусмотреть loading, пусто/ошибка API, повтор, отсутствие источников, warning, отсутствие допуска, неизвестный результат отправки. Не крутить декоративный спиннер бесконечно.

Главный механик: сводка по состоянию (по последней проверке каждой ТС; карантин только при обоснованной high-рекомендации по применимому источнику либо явно подтверждённом решении механика; failed/bad в «Требует внимания» с отметкой повторной записи, без диагноза. Три категории взаимоисключающие, суммарно 50 ТС; карантин не создаётся по одному ML-score), очередь по приоритету, фильтры по статусу/двигателю/типу, история 195 проверок, временной график последних 3–5 валидных точек, статистика по исходам/типам/двигателям, переход к машине, журнал заявок. Не путать счётчик машин и сессий. Контрольные исходные 25/23/2. Аналитика вычисляется из данных, без LLM на все 195 сессий, без выдуманных расходов и статистики отказов. Явно обозначить синтетический стенд и ML-результаты mock.

График: хронология checked_at, null при check_failed — пропуск/маркер, не нулевая точка. Сравнить сопоставимые записи одной машины и версию модели; предупредить при помехах, коротком ряде. Показать изменение/тенденцию по валидным точкам и повторяемость типа, не прогнозировать срок до поломки, не строить псевдонаучные вероятности. Пример B418HK98: 0.33 → 0.67 → 0.90 (последние две F01); тренд ухудшается по ML, нужен осмотр, но точный срок отказа неизвестен. Характеристики ремонта/фактического простоя/пробега/региона не предоставлены.

## 11. Голос и семь языков

БРИФ: голосовой ввод важен, достаточно запуска диагностики и общения с агентом; не нужно управлять всеми экранами. Р: push-to-talk/кнопка записи с явным состоянием, остановка, отобразить распознанный текст для исправления/подтверждения, затем обычный агент. Запись голоса механика и акустическая диагностика двигателя — разные вещи. Никакой записи двигателя, микрофон не начинает работать без действия пользователя. При ошибке доступа/шума/распознавания остаётся текст. Не выполнять отправку заявки на основании неуточнённой фразы. Микрофон в браузере требует безопасного контекста (HTTPS публичный стенд, localhost при разработке). Ограничить длину/размер голосовых сообщений, формат MediaRecorder, API ключ хранить на сервере; аудио не хранить после транскрипции без нужды.

Groq whisper-large-v3 (или turbo после сравнения) для мультиязычной транскрипции; поддержка языка не гарантирует точность, особенно в шумном цехе и на малоресурсных языках. Проверить реальную речь. По умолчанию не делаем TTS: не входит в уточнённый минимум. Интерфейс + ответы на семи языках: ru (Русский), uz (O‘zbekcha), kk (Қазақша), tg (Тоҷикӣ), ky (Кыргызча), hi (हिन्दी), bn (বাংলা). Список — наше решение на основе пожелания СНГ, узбекский и 1–2 индийских; при новой официальной конкретике обновить. Русский и узбекский первыми, остальные добавить одним словарём. Никаких отдельных промптов/моделей/индексов для каждого языка. Переключатель, сохранение выбора, единые ключи переводов, fallback ru без пустых надписей, шрифты для письменностей. Поиск: привести запрос к русским техтерминам, сохранить исходный вопрос; ответ на выбранном языке, технические обозначения/числа/единицы и оригинальные цитаты неизменны. Не переводить ID, исходные manual/pdf_page или коды. Для голосовой команды сопоставить автомобиль из контекста и просить уточнение при неоднозначности. План 1–2 часа на локализацию при готовом UI, срок оценочный; не тратить часы на косметические переводы в ущерб P0.

## 13. Модель бюджет и стоимость

Пользователь ранее самостоятельно подтвердил Groq API PowerShell-вызовом 21.11: openai/gpt-oss-120b, total_tokens=230; mojibake был артефактом Windows PowerShell, не проблемой API. Тест в Playground показал правильную осторожность по термостату, но неподтверждённые дополнительные процедуры: RAG и проверки обязательны. Не путать Groq (провайдер) с Grok (модель xAI). Ранее использованный GigaChat не выбран.

По показанному аккаунту Groq Free: 30 RPM, 1000 RPD, 8000 TPM, 200000 TPD для GPT-OSS 120B; 20 RPM, 2000 RPD и аудиолимиты для Whisper в показанной таблице. Это снимок аккаунта, перепроверить в день работы. Бюджет LLM максимум 300 ₽, желательно 0. Не тратить на бесконечные прогоны. Один ответ короткий, evidence top-k ограничен, история чата суммируется/ограничивается; параметры таймаута, максимальных токенов и числа tool steps; обработка 429 с видимым сообщением и retry-after, не шумные циклы. Кеш при совпадении машины, сессии, версии корпуса/модели и языка; не кэшировать/автоматически отправлять изменённые заявки. Аналитика и bad/normal-вердикт не требуют дорогостоящего LLM-вызова; текстовое объяснение по запросу. Fallback при недоступности модели — явный ограниченный режим фактов/поиска, не выдавать шаблон за AI. Не заявлять неподтверждённую скорость SLA. Не покупать платные сервисы без согласования.

С начала работы вести usage по шагам: число реальных вызовов, input/output tokens, latency, ошибки, для аудио длительность/тариф. Официальный шаблон экономики: https://drive.google.com/file/d/1TjQRRsfafywe193cGyENUNq0VkkGCQxN/view . Заполнять ближе к вечеру 27.11 по измерениям работающего продукта, сохранить формулы. Для текстового API: число вызовов × (tokens_in × цена за миллион входных + tokens_out × цена за миллион выходных) / 1 000 000 × курс валюты. Если цена в USD, использовать курс ЦБ РФ на 26.11.2026, сверить на дату. STT учесть по фактическому времени записи/тарифу и пояснить, если в шаблоне нет аудиополя. Отдельно фактический Free (при квотах), коммерческий запрос и серверная эксплуатация, без ложного «всё бесплатно». Ссылку на Excel дать без авторизации; проверять в приватном окне.
